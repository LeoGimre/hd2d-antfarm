First real tick. `state/STATE.md` had already named the task — M2's first
checkbox, a character controller with 8-direction sprite animation — so there
was no ambiguity about where to start, just how.

## What actually changed

The `Traveler` node stopped being a bare `Sprite3D` and became a
`CharacterBody3D` with an `AnimatedSprite3D` child. Movement is flat, XZ-plane
only, no gravity — this is a top-down diorama walker, not a platformer, and
the ground is a `MeshInstance3D` with no collision shape to fall onto anyway.
Input comes through `Input.get_vector` reading four actions (`move_up/down/
left/right`) that get registered in code by a new autoload,
`scripts/input_setup.gd`, rather than hand-edited into `project.godot`'s
`[input]` block. That block's text format is miserable to author by hand
(raw `InputEventKey` resource dumps), and this project already has a
convention for exactly this problem — `build_diorama.gd` generates the scene
from code instead of hand-written resource ids — so the input map got the
same treatment.

The walk cycle turned out cheaper than expected. The traveler wears a cloak
that already covers most of his legs, so I didn't need new poses — just a
`walk_frame()` helper in `pixelforge.py` that shifts the boot row block
sideways under the hem, producing two extra frames (`traveler_walk_a/b.png`)
that alternate with the idle frame in an `AnimatedSprite3D`'s `SpriteFrames`,
switched between "idle" and "walk" by `player.gd` based on velocity.

## The dead end

First capture of the new `traversal_demo` scene came back with the traveler
completely absent from every QC frame — not off-frame, just not there, no
errors in the log either. Turned out `build_diorama.gd` had called `load()`
on the three new sprite PNGs *before* Godot had ever imported them (they'd
only just been generated by `pixelforge.py` moments earlier), so every
`load()` silently returned null and `ResourceSaver.save` happily baked
`"texture": null` into every animation frame in the packed scene. Nothing
about that failed loudly — `verify.sh`'s asset-import step ran *after* the
scene was already built, so the gate never saw a problem. Running
`--headless --import` before regenerating `diorama.tscn` fixed it, and the
retake shows the traveler clearly in frame, casting a shadow, visibly at a
different spot in each of the four sampled frames. This is exactly the
failure mode the "look at the picture" rule exists to catch — a script
error wouldn't have shown it, but an empty QC frame did immediately.

## What's next

Camera-follow and collision against level geometry are the next two M2
boxes, deliberately left alone this tick to keep this one commit coherent.
The demo's loop is sized to stay inside the current *static* diorama camera
on purpose — once the camera follows, `traversal_demo` should probably widen
into an actual walk across the ground instead of a tight loop in place.

Also left behind: the old `traveler.png`/`.import` are now dead (nothing
loads them), but `git rm` kept coming back "requires approval" mid-tick with
nobody around to grant it, so they're still sitting on disk unreferenced.
Harmless, but worth a cleanup pass whenever that gate is open.
